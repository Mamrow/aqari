@AGENTS.md

## Commands

```bash
npm start                    # expo start — Metro bundler / dev server
npm run android               # expo run:android — native build + install (dev client; Expo Go won't work with MapLibre/Sentry)
npm run ios                   # expo run:ios
npm run typecheck:mobile       # tsc --noEmit (app code; tsconfig excludes supabase/functions)
npm run typecheck:functions    # deno check supabase/functions/*/index.ts (edge functions)
npm run build:android:check    # expo export --platform android — catches bundler-breaking errors before an EAS build
```

There is no lint script and no test runner configured — don't assume `npm test`/`npm run lint` exist.

Environment: copy `.env.example` to `.env` and set `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_ANON_KEY` (from the Supabase project's Settings → API) and `EXPO_PUBLIC_MAPTILER_KEY` (free tier at maptiler.com, no card required). `EXPO_PUBLIC_SENTRY_DSN` is optional — crash reporting (`src/lib/crashReporting.js`) is a no-op without it; release builds get it from EAS env. That file holds the app's only `Sentry.init`: if `npx @sentry/wizard` ever adds a second one to `App.js`, delete it (its defaults enable PII, session replay and console capture on screens full of phone numbers).

EAS builds (`eas.json` profiles `development`/`preview`/`production`) are run manually by the user — don't run `eas build`/`eas submit`.

The two GitHub Actions workflows (`.github/workflows/`) are **`workflow_dispatch` only** — never triggered by a push, because each run either spends Mac minutes or reaches installed phones. `ios-testflight.yml` runs `eas build --local` on GitHub's macOS runner (uses EAS-stored signing, doesn't burn EAS build quota); `publish-update.yml` runs `eas update --channel production` and then uploads source maps to Sentry. **`runtimeVersion` is `{ "policy": "appVersion" }`**, so an update only reaches builds whose `expo.version` in `app.json` matches: bump `expo.version` in the same commit as any native change (new native library, SDK upgrade, icon/splash), or an old build takes JS that calls native code it doesn't have and crashes on launch. The `fingerprint` policy is deliberately not used — it hashed differently on Windows/Linux/macOS, so updates silently reached nobody.

Store-screenshot automation lives in `.maestro/screenshots/` (Maestro CLI flows + a README covering the AR/EN locale-switch sequence) — a debug/dev-client build only, not a release build, since it depends on `DevSettings.reload()`.

Supabase edge functions (`supabase/functions/*`) are deployed separately via the Supabase CLI, not through the Expo build — they're plain Deno, typechecked with `deno check`.

## Architecture

**Entry point:** `index.js` → `App.js`. `App()` (wrapped in `Sentry.wrap`) blocks on an async bootstrap before rendering anything: it reads the persisted language, *writes* the `'ar'` default on first launch (AppContext only overrides its initial language if one is stored, so an unpersisted default made the two disagree), then calls both `I18nManager.allowRTL(lang === 'ar')` and `forceRTL(lang === 'ar')`. The pair is load-bearing — `forceRTL(false)` alone lets an Arabic-locale iPhone lay the English app out RTL. Render tree: `SafeAreaProvider > ErrorBoundary > AppProvider > AppShell`. `AppShell` waits for context `hydrated`, shows `OnboardingScreen` on first run (outside navigation, so it's never in a back stack), otherwise mounts `NavigationContainer` + `RootNavigator` + the always-mounted `AuthModal`. `NavigationContainer`'s `direction` is driven from the current `language`, not `I18nManager` (a launch-time snapshot), because the native stack header ignores `I18nManager` for back-button side.

**Single global context — `src/context/AppContext.js` (~1200 lines).** This is the one thing to understand before touching almost any screen or component: `useAppContext()` is called from nearly every screen/component in the tree and is the de facto integration point for five concerns that live in one file/hook:
- auth session + profile (wraps `src/lib/supabase.js`, `src/utils/otp.js`)
- Supabase row ↔ app-shape mapping via `src/lib/mappers.js` (`listingFromRow`, `listingToRow`, `profileFromRow`, `agentFromRow`, `boostPaymentFromRow`, `listingReportFromRow`)
- `isAdmin` (server-side allowlist, re-checked via the `am_i_admin` RPC whenever the auth uid changes — never trust a locally-cached admin flag)
- language/theme/onboarding-seen persistence (`src/i18n/constants.js` storage keys)
- push notification registration (`src/utils/pushNotifications.js`)

New global state almost always belongs as an addition to this context rather than a new one — that's the existing convention, not a suggestion to split it.

**Auth is phone + password on Supabase's native phone provider, with a one-time code.** Sign-up takes name/phone/password and sends a 6-digit code (`supabase.auth.signUp({ phone, password, options: { channel } })`), which `verifySignUpOtp` redeems before the `profiles` row is written — abandoning the code screen leaves no profile behind. Day-to-day sign-in is `signInWithPassword({ phone, password })` with no code at all, which is what keeps the per-message cost off the common path. "Forgot password" is `signInWithOtp({ shouldCreateUser: false })` — that flag is load-bearing, without it a typo'd number silently becomes a new account — then `verifyOtp` + `updateUser({ password })`; redeeming the code *is* the proof of ownership, so there's no admin API, no emailed link, and no service-role key anywhere in the flow. Code **delivery** is not in the app at all: Supabase generates/stores/verifies the code, and a **Send SMS Hook** (Authentication → Hooks, dashboard-configured) hands it to the `send-whatsapp-otp` edge function, which sends it over WhatsApp via Meta's Cloud API (Standard Webhooks signature check, no DB access, no state). Because the hook bypasses Supabase's own providers, `src/utils/otp.js`'s `OTP_CHANNEL` stays `'sms'` even though codes go out on WhatsApp — that's correct, not a leftover; it only has to be a value the API accepts. `verifyOtp` takes `type: 'sms'` either way. No messaging SDK or credentials live in the bundle. `docs/phone-auth-setup.md` covers the dashboard/Meta setup.

**No email address is used for authentication or recovery**, and that part is a constraint to preserve. One caveat that is easy to read past: `profiles.email` came back as an *optional contact field* the user types into Settings → Personal info (`migration_profile_email_optional.sql`, read its header) — so an email address **is** collected, even though nothing is ever sent to it and it can't sign anyone in. The store privacy labels were filled in on the basis that none was; **declare "Email Address" in App Store Connect → App Privacy and Play's Data safety form before the next submission, or remove the field.** The previous design registered each phone as a synthetic `@phone.aqari.dev` address and mailed reset links via Resend through a `send-password-reset` Edge Function — all of that (function, `profiles.email`, `get_reset_email_for_phone`, `private.password_reset_attempts`, the `aqari://reset-password` deep-link handling) is deleted; see `supabase/migration_phone_auth_no_email.sql`. (The only email anywhere is `notify-admin-review`'s optional Resend alert to a configured *admin* address, which deliberately omits the seller's name/phone.) Session storage (`src/lib/supabase.js`) is still a custom `LargeSecureStore`: a random AES key lives in `expo-secure-store` (small, but real Keychain/Keystore), the session ciphertext in `AsyncStorage` (unbounded size, but not secure storage) — plaintext tokens never touch disk.

**Roles: no buyer/agent split.** Any signed-in account can browse, list, and save. The only role branch is `isAdmin`, decided server-side; `RootNavigator` renders `AdminTabs` or `MainTabs` on that one flag.

**Listings have two independent status dimensions** (`supabase/schema.sql`, `supabase/migration_listing_lifecycle.sql`): moderation `status` (`pending` / `approved` / `rejected`, admin-controlled) is separate from lifecycle (`listing_state`, `expires_at`, `renewed_at`, 30-day auto-expiry with free renewal via `renew_listing()`, plus `is_featured`/`featured_until` for boosted listings). Both sets of columns are revoked from direct owner `UPDATE` via RLS — an owner's plain `update()` can't touch them; changes go through `SECURITY DEFINER` functions like `admin_set_listing_status`, `renew_listing`, `resubmit_rejected_listing`. The same revoke-column/gate-via-RPC pattern is used repo-wide, not just for listings — e.g. `agents.verified` (the agent trust badge) is only settable through `admin_set_agent_verified` (`supabase/migration_agent_verified.sql`).

**Reads are gated the same way, and one of them constrains how you query.** `listings` SELECT is `status = 'approved' or owner_id = auth.uid() or private.is_admin()` (`migration_listings_read_approved_only.sql`), and on top of that `anon` has no SELECT privilege on `agent_phone`/`agent_id` — both hold a seller's phone number (`migration_hide_seller_phone_from_anon.sql`). RLS hides rows, never fields, so that half is Postgres column privileges, which has two consequences worth knowing before touching any listings query: a column-level revoke is ignored while a table-level grant stands (so SELECT is revoked from `anon` wholesale and granted back column by column), and `select('*')` then fails *entirely* for a signed-out caller rather than dropping the forbidden columns. Hence `fetchListings` picks `'*'` when `authUid` is set and `LISTING_PUBLIC_COLUMNS` (`src/lib/mappers.js`) when it isn't — that list and the GRANT must stay in step, and a new column needs adding to both. The generated `has_contact` boolean exists for the same reason: the detail screen decides whether to show Call/WhatsApp from it, since a signed-out visitor can't see the number to test. Contact actions resolve the number at tap time via `fetchListingContact`, because a listing loaded while signed out never carries one.

**Boost/featured payments** run through four Libyan payment gateways (Edfali, Sadad, Moamalat, MasrefyPay) via a third-party processor (Dpay), orchestrated by `src/components/BoostListingSection.js` and three edge functions: `create-boost-payment` (server looks up the LYD price — never trust a client-supplied price — and opens a `boost_payment_sessions` row), `verify-boost-payment` (submits the OTP the user got from their wallet app, server-to-server), and `dpay-webhook` (Dpay's signed `payment.*` callback — the *only* confirmation path for Moamalat, which has no OTP/verify step, and an idempotent backstop for the others if `verify-boost-payment`'s response never reached the app).

**Supabase edge functions** (`supabase/functions/*`, Deno) are the only place the service-role key is allowed to exist — used for account deletion (`delete-account`), the cron-driven listing lifecycle sweep (`lifecycle-cron`, auth'd by comparing the caller's bearer token to the service-role key itself since it's only ever invoked by `pg_cron`/`pg_net`), and push/notification fan-out: `notify-listing-status` (approved/rejected, to the owner) and `notify-new-listing` (approval, to users following that city — the one place other accounts' push tokens are read, which is why it's server-side), both triggered by **dashboard-configured** Database Webhooks on `listings` UPDATE (no way to create those from SQL); and `notify-admin-review` (push to admins, optional email, when a listing enters `pending`), fired by a DB trigger from `migration_admin_review_notifications.sql`. The notify-* functions authenticate with a shared `DB_WEBHOOK_SECRET` header, *not* the service-role key — see `notify-listing-status` for why. `send-whatsapp-otp` is the auth Send SMS Hook described above. Each function has substantial rationale comments explaining *why* — read them before changing auth/webhook logic there, the reasoning usually isn't obvious from the code alone.

**Database migrations** are flat, unnumbered `supabase/migration_*.sql` files plus a base `supabase/schema.sql` — there's no migration-runner/ordering convention beyond file naming and git history. Check `schema.sql` for current table shape rather than assuming a migration file is the latest word on a column.

**i18n**: `src/i18n/translations.js` is a flat `{ ar: {...}, en: {...} }` key→string dict (Arabic is the default/fallback in `useT()`, not English). `useT()` itself depends on `useAppContext()` for the current `language`, so anything needing translated strings transitively depends on `AppContext.js`.

**RTL layout is auto-mirrored by Yoga/Fabric even for values you'd expect to be physical.** Verified live on-device (RN 0.81, `newArchEnabled: true`) with `I18nManager.isRTL` confirmed `true`: `alignItems: 'flex-end'`/`'flex-start'` on a column's cross axis, and a `Text`'s own `textAlign: 'left'`/`'right'`, both get mirrored under RTL — setting `writingDirection`/`direction: 'rtl'` alongside them does **not** exempt them. So in RTL-specific style branches (see `OnboardingScreen.js`'s `copyBlockBandRTL`/`titleRTL`/`bodyRTL`), `'flex-start'`/`'left'` is what actually renders visually-right under `isRTL: true` — the intuitive-looking `'flex-end'`/`'right'` renders backwards. Don't "fix" these back to the intuitive values without re-verifying live on an RTL device/emulator.

**Store-guideline feature flags** (`src/config/features.js`): a compliance-driven kill switch, not a generality — e.g. `BOOST_PURCHASES_ENABLED` hides every visible trace of the Boost/Featured billing flow (purchase UI, featured badges, payment-history screens) without removing the underlying edge functions/tables, because Apple/Google IAP rules don't have a realistic path for the existing Libyan DPay gateways yet. Read the comment on a flag before assuming it's dead code to delete.

**Maps are split per platform** in `src/components/map/`: Metro resolves `ListingsMap.android.js` / `SimpleMap.android.js` (MapLibre + MapTiler) on Android and the `.ios.js` versions (`react-native-maps` with **no `provider` prop**, i.e. Apple Maps) on iOS. Screens just import `../components/map/ListingsMap` and never branch on `Platform`; anything expressed differently per library (regions vs bounds, zoom vs deltas, visible-count reporting) stays inside those files. Never pass `PROVIDER_GOOGLE` — avoiding Google's billing-gated SDK key is why Android is on MapLibre (Mapbox was also ruled out for requiring a payment method). Android style comes from `src/theme/mapStyle.js`'s `getMapStyleUrl(theme)` (keyed by `EXPO_PUBLIC_MAPTILER_KEY`). Clustering is shared pure-JS `supercluster` in `useListingClusters.js` so both platforms group identically; it's currently switched off via `CLUSTERING_ENABLED = false` (a "for now" density decision — the code path is kept intentionally). Pin views (`PricePin`, `ClusterBubble`) are shared in `MapPins.js`.

**Block/report (App Store Guideline 1.2 UGC safety)**: buyers can block a seller by phone number (`blocked_sellers` table, `supabase/migration_blocked_sellers.sql` — keyed on `owner_id`/`blocked_phone`, not a FK to `agents`, since a phone stays blockable after its directory entry is gone) on top of the pre-existing listing-report flow. `src/utils/contactActions.js` centralizes the `tel:`/`wa.me` deep links so both the block check and the "no app installed" error feedback happen once for every call site (buyer and admin).

## Conventions

**Plain JavaScript, no TypeScript sources** — every file in `src/` is `.js`. `npm run typecheck:mobile` runs `tsc --noEmit` against `expo/tsconfig.base` with `checkJs` off, so it catches config/dependency-level breakage, not type errors in app code. There is no type safety net; `prop-types` is a dependency but unused.

**Styling**: `StyleSheet.create` per file (no shared stylesheet, no styling library), with all colors read at render time from `useThemeColors()` (`src/theme/useThemeColors.js` → `src/theme/colors.js`) rather than hardcoded — only light/dark neutrals flip, the single blue accent, `WHATSAPP_GREEN` and `FEATURED_GOLD` are fixed in both themes. Every touchable spreads `pressedStyle` from `src/theme/press.js` as the last entry of its `style` array (`style={({ pressed }) => [styles.btn, pressed && pressedStyle]}`) — that one opacity value is what makes presses feel uniform app-wide; don't hand-roll a per-component pressed variant.

**User-facing strings always go through `useT()`** and must be added to *both* `ar` and `en` in `src/i18n/translations.js` — Arabic is the fallback, so a missing `en` key renders Arabic rather than failing loudly.

**Enumerations live in `src/data/`** (`propertyTypes.js`, `districts.js`, `countries.js`, `listingStatus.js`, `reportReasons.js`), and their values are what the database columns store — changing a value there is a data migration, not a UI edit.
